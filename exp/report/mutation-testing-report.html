变异测试调研与可落地分析报告§

本报告基于一次 StrykerJS 实地实验。论断分三级背书：实测指本机实验产出，证据位于 exp/ 下可复现文件，数字由构建脚本从源数据直接生成；官方指 Stryker 官方文档或 GitHub API，访问日期 2026-10-22，URL 见证据总表；推断指由前两级证据合理外推，显式标注，不作硬结论。实验协议、数据字典与复现命令见附录。

环境基线实测：data/runs.jsonl 环境字段：8 核 Cortex-A32，15G 内存，node v24.19.0，StrykerJS 10.0.0，两仓分别冻结于 d1a8d16（showdown）与 223a6ce（sql-formatter）。机器为共享环境，外部负载均值最高观测到 17-30，全部计时结论附方差声明。

术语速查§

常用术语 18 条（点击收起）
术语意思
变异体（mutant）对源码的一处小改动，例如把 >= 换成 >、把字符串换成空串。每个变异体模拟一个具体缺陷。
杀死（killed）变异体激活时至少一个测试失败，说明套件能区分正确代码和这个缺陷形状。这是想要的结果。
存活（survived）变异体激活时全部测试仍然通过，没有任何断言能发现这个缺陷形状。
干跑（dry run）正式变异前先把原套件完整跑一遍。Stryker 借此确认套件本来全绿、登记全部测试、记录每个测试覆盖了哪些代码。之后每个变异体只跑覆盖它的那部分测试，这是最大的提速来源。
变异分数(killed + timedOut) / total，error 状态不计入分母官方：D3。
NoCoverage该变异体所在代码没有任何测试执行过，直接按存活计。
timedOut / hitLimit变异体造成死循环时，单个测试有执行次数上限，超限按 killed 计。hitLimit 就是这个上限的配置名。
静态变异体位于模块加载时执行一次的代码（如文件顶层常量）。运行时开关切换不到它，要跑就得为它重建整个测试环境。加载期和测试期都会执行的叫混合静态。
ignoreStaticStrykerJS 选项。开启后纯静态变异体标记为 Ignored，不跑也不计分。
schemata（变异切换）免重编译的激活方式：代码被改写成 global.activeMutant === '1' ? 变异值 : 原值，运行时设一次变量即激活一个变异体官方：D8。
并发 workerStryker 按配置并行的测试进程数。沙箱只是文件拷贝，worker 之间共享同一个目录官方：D10。
等价变异体改动不改变任何可观察行为（如 x + 0 改成 x - 0），原理上不可能被杀，官方无检测与标记机制官方：D7。
写手（本实验）盲法 LLM 子代理，在无 git、无网的沙箱里按刺激清单补测试。A 臂看存活变异体清单，B 臂看未覆盖行清单，C 臂是冻结套件本身。
帧（frame，本实验）圈定的变异与刺激文件集合：showdown 取 4 个缺陷相关文件，sql-formatter 取 8 个文件。两臂同帧，保证可比。
headroom（本实验）冻结套件检不出的历史缺陷，各臂唯一有机会补抓的洞，共 5 个。
污染层（本实验）修复提交自带的回归测试已在套件里，反向应用缺陷后基线立刻检出，没有提升空间，共 20 个。
差分检出（本实验）判定要求两个条件同时成立：带缺陷时失败，无缺陷时通过。一个总是失败的坏测试拿不到分。
killed 集合翻转（本实验）同一变异体在不同并发配置下判定相反（killed 变 survived 或反之），来自负载敏感测试。

1. 摘要与决策矩阵§

1.1 四问四答§

问一：变异测试值不值得引入？§

值得。定位是定向补强工具，先不当质量门禁用（理由见 1.3 陷阱一）。它测的是覆盖率测不出的东西：无断言刷覆盖的测试在覆盖率口径满分，在变异口径现形官方：docs/。实测中变异引导的写手把变异分数从 66.3% 提到 69.0-69.1%，810 个变异体多杀 17-18 个实测：data/scores.jsonl。

问二：怎么上？§

按第 7 章四级路线图分阶段上：本地探索 → 夜间批跑 → CI 软门禁 → 硬门禁。硬门禁有四项前置条件（判定稳定性、分母钉死、端口卫生、计时敏感测试预检），全部来自实测踩坑。直接上硬门禁会随机挂掉无辜提交（见 1.3 陷阱一）。

问三：什么时候不上？§

三种情况。测试套件本身跑得慢（变异测试成本是套件时长乘以变异体数，套件 2 分钟、400 变异体就是小时级）实测：runs.jsonl。集成测试占比高或测试绑端口绑进程（并行 worker 共享目录，冲突产生假击杀）官方：parallel-workers实测：s_c4_r1 干跑翻车。团队还在追行覆盖率（先用覆盖率找未覆盖区，变异测试的第二阶段才是断言强度）实测：5.3 节位置彩票发现。

问四：预算几何？§

一次性接入成本 1-2 人日（配置、冒烟、端口预检）。运行成本实测：全量首跑以小时计（showdown 单文件 401 变异体 conc2 需 1183-1315 秒）实测：runs.jsonl，增量模式把日常成本压到基线的 4-9%（1/10/100 行改动分别省 96%/95%/91% CPU）实测：runs.jsonl ladder 行。夜间批跑 + 增量是性价比配置。

1.3 陷阱速览（详见第 6 章）§

  1. 判定不稳定：同配置同套件，并发 1 与并发 2 的 killed 集合差 27 个（10.5%），负载敏感测试（ReDoS 计时断言）在并发下随机翻车。实测
  2. 分母陷阱：一个动态 import 测试让 35 个 Ignored 变异体涌入分母，分数反降到 64.8%。加测试可以让分数下降。实测：scores.jsonl b3

2. 问题定义：变异测试解决什么§

行覆盖率只回答"这行代码被执行过吗"，不回答"执行后有没有被检查"。官方的比喻：三明治覆盖率告诉你面包 80% 涂了酱，变异测试告诉你那是不是巧克力酱官方：D2。无断言纯刷覆盖的测试在覆盖率口径满分。

机制上，向源码注入缺陷（变异体），跑既有测试。测试挂则变异体被杀；全绿则存活。存活即存在一个真实缺陷形状，套件抓不住官方：D2。变异分数 = (killed + timedOut) / total，error 状态剔除分母官方：D3。算子覆盖算术、逻辑、等号边界、布尔、字符串、正则等 16 类 30+ 变体，三实现命名对齐官方：D6。

实测对照：我们挖出 26 个历史真实缺陷（反向应用 bugfix 的源码侧），冻结套件对其中 5 个全绿（headroom）实测：E5。这 5 个就是变异测试要抓的那类洞。但同样实测表明，存活变异体指引与这些洞的位置错位（见 5.3）。

Stryker 只变异源码、不碰测试官方：D2，实现走 mutant schemata：代码改写为 global.activeMutant === '1' ? 变异值 : 原值，运行时激活，免每变异体重编译官方：D8。

3. 生态与选型§

Stryker 有三个实现【G1-G3】：StrykerJS（3264★，2016 起，十年维护，Apache 2.0，Info Support 公司支撑 + 社区）为旗舰；Stryker.NET（2107★）填补 .NET 空白官方：D5；Stryker4s（217★）生态最小。三仓 2026-10 均有活跃 push。PHP 生态对标 Infection 2264★【G4】；Java 的 PIT、Python 的 mutmut 为对应主力（背景知识，本次未验证，标注推断）。

JS/TS 侧的 runner 矩阵：Jest、Vitest、Mocha、Jasmine、Karma、Cucumber、Tap 七个专用 runner 加 Command 兜底；Jest/Vitest 的增量支持为 Full 档（测试级精确 diff），Jasmine/Karma 只有测试名官方：D9。实测两仓分别用 vitest 与 jest runner 跑通全流程实测：E7-E9。

工程适配成本方面有三处需要预检（实测经验）：其一，vite 插件桥接源码的仓需要 vitest.related=false（模块图断链致零测试被发现）实测：logs/stryker-smoke.log。其二，DisableTypeChecks 预处理器会污染被当作预期输出的 .html 夹具，纯 JS 仓应关掉实测：同上。其三，pnpm 管理的仓需从项目外 neutral 目录用钉定 pnpm 版本安装，npm 11 的 devEngines 会拦项目内调用实测：logs/funnel-stage3.log。

hitLimit：默认对 1e6 配对，状态分布零差异，墙钟差在噪声带内实测：E7 hl_high。本规模无可测效应。

5. 收益实测（RQ2）§

5.1 缺陷池与污染率§

26 个有效反向应用缺陷中，20 个（74%）被冻结基线套件直接检出实测：E4/E5。机制：成熟仓库的修复提交自带回归测试，测试在 HEAD 里，反向应用源码侧后测试即挂。这一污染率与实验设计阶段三位独立审阅模型的预测一致（对照记录见 data/protocol.md 修正案）。含义：成熟仓库里"历史缺陷"大多已不是变异测试的靶子；靶子是从未有过测试的代码。

5.3 三个机制发现§

发现一：位置彩票§

headroom 缺陷全部住在未覆盖代码里。A 臂刺激限定 state=Survived，而未覆盖区的变异体是 NoCoverage，存活引导在结构上指不到那里；B 臂的未覆盖行引导恰好指过去。A-B 之差是引导地理与缺陷地理的错位，不是写手能力差实测：E12 + data/sd-uncovered.jsonl + E6。

发现二：满分假安慰§

--!> 缺陷所在的 regexes.js，其全部变异体在引导跑中已被杀灭（该文件分数满分），故 A 臂刺激根本不含该文件；真缺陷却在。变异分数满分的区域仍可能有缺陷：分数只衡量套件对已生成变异体的断言强度，这些算子没生成到的缺陷形状它管不到实测：E9 + E4。

发现三：b3 分母陷阱§

B 臂写手 b3 的一个动态 import 测试在测试运行期重新执行了模块加载代码，Stryker 的静态判定全部失效：35 个 Ignored 变异体涌入分母、其中 26 个存活，分数 64.8% 低于基线 66.3%。复跑确认可复现，非负载噪声。加一个测试可以让变异分数下降，且分母构成静默改变实测：E8 b3 行，Ignored=0。

7. 落地路线图§

7.1 四级采用§

L1 本地探索（第 1 周）§

工程师本地 npx stryker run --mutate <改动文件> 看存活清单。无流程改动，纯信息增量。配置模板见 7.2。前置：跑通一次全量（获得基线分数与静态体 census）。

L2 夜间批跑（第 2-4 周）§

增量模式 + 固定并发数 + ignoreStatic 视文件形状。产物只进报告不进门禁。团队建立"存活清单分类"的手感：可杀（补断言）、等价（标记忽略）、不划算（记录跳过）。

L3 CI 软门禁（第 2 月）§

分数下降在新 PR 上打标签但不阻塞；翻转与分母变化自动归因（比较 counts_by_state 而非只看总分）。此阶段收集判定稳定性数据。

L4 硬门禁（数据背书后）§

四项前置全部满足才准上：

  1. 连续 4 周跨并发 killed-set 翻转率 < 1%（本实验基线 10.5%，来自计时敏感测试）；
  2. 分母钉死：Ignored 计数在相邻运行间零漂移（防陷阱 2）；
  3. 端口卫生预检通过且 CI 并发数锁定（防陷阱 1/8）；
  4. 阈值定在实测分布的 P5 而非 100（防陷阱 4）。

任一不满足则停留在 L3。

7.3 运行预算参考（外推自实测，标注推断）§

100 文件中型 TS 仓、套件 90 秒、约 8000 变异体：全量首跑约 6-9 小时（8 核 conc2-4）；接入增量后日常 <30 分钟。两条纪律：一是先把套件时长压进 2 分钟（变异成本与其线性相乘）实测比例关系；二是 CI 容器核数与本地一致，否则分数不可比实测：并发翻转。

8. 结论§

值得引入，但只以定向诊断工具的形态，且先解决两个前提；本实验未支持它作为质量门禁或真缺陷检出增强器的用法。

成本侧理想。增量模式把日常开销压到基线的 4-9%（1/10/100 行改动省 96%/95%/91% CPU），边际成本随改动规模走实测：runs.jsonl ladder；静态密集的纯数据文件很便宜（987 体 8 分 50 秒）实测：E9；断点续跑可用。

质量侧不理想。预注册主判定为无功效的 null（A 0/5，B 1/5，p=1.0）实测：E6，且机制证据偏向结构性负面：headroom 缺陷全部住在未覆盖区，存活变异体指引的恰好是已覆盖但断言弱的区域，引导地理与缺陷地理错位实测：E4/E12；变异分数满分区域藏着基线漏检的真缺陷实测：E9；唯一被检出的缺陷由覆盖引导抓住。分数从 66.3% 提到 69.0-69.1% 是写手对着被引导指标补断言的直接回报，自循环成分高，它证明的是诊断能力（哪里断言弱），不是缺陷检出增益。

引入方式§

按 7.1 路线图走：L1 本地探索起步，L2 增量夜间批跑，L3 CI 软门禁，L4 硬门禁等四项前置实测达标（跨并发翻转率 <1%、Ignored 计数零漂移、端口预检、阈值定 P5）。测试套件超过 2 分钟或集成测试占比高的团队先解决套件速度，再谈接入。

放弃的预期§

三样：分数当硬门禁（判定跨并发翻转 10.5%实测：E7）；拿存活清单直接指导补测试去抓真缺陷（先看覆盖）；死磕 100 分（约 10% 引导目标为等价体实测：E11）。

结论

变异测试是断言强度体检仪，不是缺陷检出增强器。它最可靠的产出是"哪里断言弱"的清单和省 91-96% 的增量管线；它管不到变异算子没生成到的缺陷形状，也指不到从未被测试过的代码。先覆盖率后变异，先诊断后门禁。
